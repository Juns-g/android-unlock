# HyperOS standalone validation

## Accepted physical unlock and terminal receipt limit

On 2026-10-16, the owner-authorized, unchanged standalone App built from `749f2f4c1ba6ca46b9619f541bae23933a6c4722` physically unlocked the MIX Flip / Android 16 / HyperOS `OS3.0.305.0.WNICNXM`. The controlled start was online, secure user 0, locked and screen off. A fresh process read the Keychain noninteractively (`read_success`, status 0), prepared the verified empty keypad and dispatched six standard digit key events. Before reaching the sixth action, the guarded loop had verified the preceding source-bound progress and full identity/freshness checks. The authorized command took 40.578 seconds.

The original CLI result remains `partial_input_aborted_no_retry` / exit 3, with `pinProfile=hyperos_pin`, `actionsAttempted=6`, `adbSucceeded=6`, and `inputObservation.reason=hyperos_progress_source_unverified`. The sixth source acknowledgement was not verified. The exact event invalidation mechanism has not been established; withdrawal of the authenticated field during the transition is a plausible explanation, not a proven event trace.

An immediate separate `status` process reported `observed`, online, awake, secure, Android user 0 and unlocked. An additional keyguard read reported `showing=false`, `mIsShowing=false`, `mInputRestricted=false` and `occluded=false`. This establishes physical completion while preserving the CLI error. No additional digit, clear, retry or automatic relock followed. The temporarily isolated keepalive job was restored.

For this exact tested six-digit baseline and receipt combination only, obtain one fresh read-only `android-unlock-hyperos status --serial SERIAL` for the same explicit target. If it independently reports observed/online/awake/secure/user0/unlocked, report the phone as physically unlocked and the CLI as a terminal false negative. Never rewrite the original JSON/exit code or invent a sixth acknowledgement. A locked or unknown result, incomplete dispatch, another error, or identity/user changes remains stopped. This is not a general wrapper for treating exit 3 as success.

Keep the already authorized working App frozen. No PIN enrollment or further Keychain approval is needed for this installed baseline. Correcting the CLI terminal classification would require a separately reviewed implementation and new-signature acceptance; it is deferred rather than replacing this working installation solely to polish the receipt. Earlier sections below record the preceding investigation stages; their pending results do not supersede this accepted physical test.

This branch combines the strict HyperOS keypad profile from `1912ed9` with the previously accepted ColorOS code, and provides an optional separately signed HyperOS App so an enrolled default helper can remain unchanged.

The HyperOS profile recognizes the observed `keyguard_pin_view` / `pin_container` ancestry, an empty or bullet-only `PasswordTextView` `pinEntry`, ten distinct resource-ID digit targets, and matching delete/emergency geometry. The current candidate sends standard digit key events through the pinned OEM keypad handler and requires source-bound entered-count evidence before each next action. It neither clears an existing prefix nor dispatches Enter after the final digit. Unknown identity, focus, state, geometry or progress stops the attempt.

The compile-time `HYPEROS_STANDALONE` variant fixes its bundle identifier to `page.juns.AndroidUnlockHyperOSHelper` and its only eligible credential/unlock path to `~/Applications/AndroidUnlockHyperOSHelper.app/Contents/MacOS/android-unlock`. It does not accept a runtime path override. The default identifier/path and shared exact UID/serial/user Keychain account remain unchanged. A new signature still needs the owner's native authorization for an existing PIN item.

Both build variants pass the combined offline checks, including existing ColorOS, Vivo, Flyme, AOSP and HyperOS fixtures. A staged standalone installation verifies its separate bundle, launcher and collector while retaining the default enrolled binary. These facts alone do not establish fresh-process Keychain access or physical HyperOS PIN unlock.

Real-device acceptance is pending. Initial preparation-only observations found that the phone could return to dozing immediately after a wake request, with the power service reporting an application sleep reason. No credential or PIN input was used during this investigation, and no biometric, device security or power configuration was changed. The normal SystemUI identity checks and wake-only event remain enforced.

Further inspection identified a focused `com.miui.aod:id/shortcut_view_left` on the ordinary lockscreen. Generic parsing correctly rejects an unknown focused clickable control; sending Space to that control is inappropriate. A separate cover verifier now requires the exact SystemUI root/header and AOD shortcut ancestry, classes, flags, unique nodes and contained nonoverlapping geometry. It permits focus only on that precise shortcut, rejects editable/password content and credential pages, and requests the system authentication page without touching or activating the shortcut. Generic AOSP/Vivo/Flyme/ColorOS parsing is unchanged.

The revised preparation-only device test and built candidate dry-run reached `ready` / `hyperos_pin` with count 0, verified SystemUI identity and a locked secure user 0. Both build variants pass 653 synthetic checks. This remains distinct from a successful Keychain read and physical PIN unlock. During one diagnostic, an existing periodic keepalive job was temporarily paused to isolate concurrent wake events and restored afterward; it was not reconfigured. The installed default helper remains unchanged.

For owner handoff, keep the phone unfolded and manually unlocked, then personally run `android-unlock-hyperos authorize-existing --local-user --serial SERIAL` for the existing item. A same-process authorization receipt is not proof of persistent access. The final acceptance requires a new authorized process, one complete guarded PIN attempt, and an independent same-device/user keyguard readback.

## Confirmed invisible accessibility progress

The owner confirmed that the extra USB-debugging security option was already enabled. Nonsecret Home, Back and a freshly located Settings back-button tap produced independently observed window transitions. Early observations taken during the transition were inconclusive; they must not be cited as evidence that input injection is blocked.

A subsequent metadata-only hierarchy inspection found a visible `delete_button` under `keyguard_selector_fade_container`, outside the empty `delete_container` checked by the original profile. Empty accessibility text is therefore not sufficient proof of an empty PIN field on this build.

Static inspection of the owner's SystemUI program (SHA-256 `6972e29c511b078a62612646c53039865c4fb140dc24b90d9d7035532435af66`) supports this discrepancy: `PasswordTextViewForPIN` has its own dot list and `onAppend` implementation, but inherits `getTransformedText` from `MiuiPasswordTextView`, which reads a different list. The subclass also reports the generic `PasswordTextView` accessibility class. This is an explanation for missing progress, not permission to infer that all dispatched digits were accepted.

The profile now requires the verified footer cancel button for an empty field, rejects a visible footer delete button with empty text, and validates footer ancestry, shape, uniqueness and nonoverlapping geometry. Existing partial input must stop before credential access. Both build variants pass 671 synthetic checks. A candidate dry-run against the owner's retained dot stopped with `hierarchy_hyperos_entered_progress_unavailable`, `secure_empty_pin_target_unverified`, `credential=not_queried` and `submitted=false`. This correction does not yet implement reliable shaped-PIN progress or establish successful physical unlock. The enrolled Apps were not replaced for this diagnostic.

`diagnostics/HyperOSProgressProbe.java` is a separate, bounded read-only investigation tool. It binds the observed SystemUI field and reports only source identity checks and text-change index/count metadata. It never requests node/event text, injects input, reads credentials or joins the production collector. Its ready frame reports footer cancel/delete presence; event frames report sequence, same-source, source-shape, same-window, password flag, event-class match, from-index, removed-count and added-count. It exits after three minutes or eight matching events. These frames are diagnostic evidence only, not production acceptance.
